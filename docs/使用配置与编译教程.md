# StardewMod 使用、`mod.toml` 配置与编译教程

本文面向两类人：

1. 想直接使用这个模组的人。
2. 想从源码编译、调试、打包这个模组的人。

这份仓库里有三套不同层级的配置，先分清楚职责：

- `config.json`
  只存放模组菜单快捷键、界面倍率这类本地 UI 配置。
- `mod.toml`
  只存放 LLM 全局文本配置，例如 provider、URL、Token、模型、超时、感知半径等。
- 存档内 NPC 设置
  每个 NPC 的启用状态、Provider 选择、时间窗、行为/对话/日程控制开关，不写进 `mod.toml`，而是在游戏内菜单里按存档保存。

当前 `config.json` 里最值得注意的字段有：

- `OpenMenuKey`
  打开模组菜单的快捷键，默认是 `L`。
- `MenuScaleIndex`
  整个模组菜单树共用的界面倍率。
- `NpcPerceptionRadiusTiles`
  旧版感知半径回退值。主配置已经迁移到 `mod.toml` 的 `[perception].npc_radius_tiles`，正常情况下优先改 `mod.toml`。

## 1. 模组功能概览

这个模组目前主要有两块功能：

- `NPC 路线编辑`
  用于查看和编辑可编辑 NPC 的日程与路径规则。
- `NPC LLM`
  用于给村民启用 AI 行为，配置 Provider、轮询周期、每周时间窗，并查看最近的调试信息。

默认快捷键是 `L`。进入存档后按 `L` 可以打开或关闭模组主菜单。

## 2. 安装与首次运行

### 2.1 前置要求

- 已安装《Stardew Valley》
- 已安装 SMAPI
- 已把本模组放进游戏的 `Mods` 目录

模组目录最终应类似下面这样：

```text
Stardew Valley/
└── Mods/
    └── StardewMod/
        ├── manifest.json
        ├── StardewMod.dll
        ├── mod.toml
        ├── Personality/
        └── image/
```

### 2.2 首次启动会发生什么

如果模组目录里没有 `mod.toml`，模组启动时会自动生成一份默认模板。  
也就是说：

- 从源码仓库直接运行时，编辑仓库根目录下现有的 `mod.toml`。
- 从打包后的 zip 安装时，如果 zip 里没有 `mod.toml`，第一次通过 SMAPI 启动后会在模组目录自动生成。

### 2.3 游戏内使用流程

1. 通过 SMAPI 启动游戏。
2. 进入任意存档。
3. 按 `L` 打开模组主菜单。
4. 根据用途选择：
   - `NPC 路线编辑`：进入 NPC 列表，编辑日程与路径。
   - `NPC LLM`：进入 villager 列表，配置每个 NPC 的 LLM。

### 2.4 `NPC LLM` 菜单怎么用

进入 `NPC LLM` 后，建议按下面顺序操作：

1. 先确认 `mod.toml` 里至少有一个可用聊天模型 provider。
2. 在 NPC 列表页选择一个村民。
3. 在设置页里逐项配置：
   - `LLM 开关`：是否启用这个 NPC 的 Agent。
   - `Provider`：在 `mod.toml` 中已配置且可用于聊天的 provider 之间轮换。
   - `行为控制`：允许或禁止移动、动作、表情等行为。
   - `对话控制`：允许或禁止通过 NPC 对话框回应玩家。
   - `日程控制`：允许或禁止修改未来 schedule。
   - `周期 +/- 5 秒`：设置周期轮询间隔，实际范围会被限制在 `10` 到 `600` 秒之间。
   - `时间窗`：按星期配置 Agent 生效时间段。

补充说明：

- 顶部的 `全部开启(全天)` 会把所有 NPC 的时间窗直接改成每周 `06:00-26:00`。
- 如果某个 provider 没出现在菜单里，通常不是 UI 问题，而是这个 provider 当前不满足“可用于聊天”的条件。
- NPC 的这些设置是按存档保存的，不会写回 `mod.toml`。

### 2.5 调试命令

模组注册了 3 个 SMAPI 控制台命令：

```text
npc_llm_state <NPC内部名>
npc_llm_schedule <NPC内部名>
npc_llm_prompt <NPC内部名> <文本>
```

示例：

```text
npc_llm_state Abigail
npc_llm_schedule Abigail
npc_llm_prompt Abigail 今天过得怎么样？
```

### 2.6 调试与记忆文件位置

NPC 相关的本地数据会写到：

```text
Mods/StardewMod/NpcMemories/<存档名>/<NPC内部名>/
```

常见文件：

- `profile.json`：NPC 基础画像。
- `events.jsonl`：事件记忆。
- `days.jsonl`：日终总结。
- `debug.jsonl`：最近的调试摘要。
- `vectors.json`：embedding 向量缓存。

## 3. `mod.toml` 配置教程

### 3.1 文件位置

`mod.toml` 位于模组根目录：

```text
Mods/StardewMod/mod.toml
```

源码仓库里对应的是仓库根目录下的 `mod.toml`。

### 3.2 一个最重要的理解

`mod.toml` 只负责“全局 LLM 运行配置”，不负责“某个 NPC 今天几点启用、用哪个 provider”这类 per-NPC / per-save 设置。

换句话说：

- `mod.toml` 负责提供模型连接能力。
- 游戏内菜单负责把这些能力分配给具体 NPC。

### 3.3 当前文件结构

当前 `mod.toml` 主要分成这些段：

- `[router]`
- `[embeddings]`
- `[debug]`
- `[perception]`
- `[broadcast]`
- `[providers.<name>]`

其中 `providers.<name>` 可以有多个，`<name>` 是你自己取的名字，例如：

- `deepseek`
- `embedding`
- `anthropic_default`

这个名字会直接出现在游戏内的 Provider 选择列表里。  
但只有“可用于聊天”的 provider 才会出现在 NPC 设置菜单中。

### 3.4 `[router]` 全局请求行为

```toml
[router]
default_timeout_seconds = 10
max_retry_count = 2
tool_loop_max_rounds = 4
retry_backoff_milliseconds = 1500
enable_verbose_debug = true
```

字段说明：

- `default_timeout_seconds`
  全局默认超时秒数。若某个 provider 没单独设置 `timeout_seconds`，就会回退到这里。
- `max_retry_count`
  请求失败后的重试次数。实际总尝试次数是 `1 + max_retry_count`。
- `tool_loop_max_rounds`
  一次工具调用对话最多循环多少轮。
- `retry_backoff_milliseconds`
  每次重试之间的退避等待时间。
- `enable_verbose_debug`
  是否输出更详细的控制台调试日志。

建议：

- 开发调试时可以保留 `true`。
- 日常游玩如果嫌控制台太吵，可以改成 `false`。

### 3.5 `[embeddings]` 记忆检索配置

```toml
[embeddings]
provider_name = "embedding"
```

字段说明：

- `provider_name`
  指向某个已经在 `[providers.<name>]` 中定义过的 provider 名称。

注意事项：

- 这里填的名字必须真实存在。
- 当前实现不支持把 Anthropic-compatible provider 用作 embedding provider。
- 如果你不想启用语义检索，可以把它改成空字符串：

```toml
[embeddings]
provider_name = ""
```

这样模组会跳过 embedding 生成与语义检索。

### 3.6 `[debug]` 调试摘要选项

```toml
[debug]
save_request_summary = true
save_response_summary = true
save_tool_calls = true
save_patch_diff = true
save_embedding_hits = true
```

这组字段已经纳入配置模型，用于调试摘要相关的开关语义。当前版本里，最直接可见的调试噪音控制仍主要是 `router.enable_verbose_debug`。如果你后续准备收敛调试数据，可以优先保留这一组字段的语义不变。

### 3.7 `[perception]` 感知范围

```toml
[perception]
npc_radius_tiles = 100
```

字段说明：

- `npc_radius_tiles`
  NPC 的感知半径，单位是 tile。

校验规则：

- 必须大于等于 `1`。

### 3.8 `[broadcast]` 邻域广播

```toml
[broadcast]
max_hops = 5
```

字段说明：

- `max_hops`
  NPC 之间广播/扩散的最大跳数。

校验规则：

- 必须大于等于 `1`。

### 3.9 `[providers.<name>]` provider 配置

当前仓库根目录示例里有三种 provider：

```toml
[providers.deepseek]
kind = "openai"
base_url = "https://api.deepseek.com/v1"
api_key = "PUT_YOUR_TOKEN_HERE"
model = "deepseek-chat"
max_tokens = 1536
thinking_enabled = false
temperature = 0.7
tool_calling_required = true
timeout_seconds = 10
```

```toml
[providers.embedding]
kind = "openai"
base_url = "https://api.siliconflow.cn/v1"
api_key = "PUT_YOUR_TOKEN_HERE"
model = "BAAI/bge-large-zh-v1.5"
max_tokens = 1536
thinking_enabled = false
temperature = 0.7
tool_calling_required = true
timeout_seconds = 10
```

```toml
[providers.anthropic_default]
kind = "anthropic"
base_url = "https://api.anthropic.com/v1"
api_key = "PUT_YOUR_TOKEN_HERE"
model = "claude-3-7-sonnet-latest"
max_tokens = 1536
thinking_enabled = false
temperature = 0.7
tool_calling_required = true
timeout_seconds = 45
```

字段说明：

- `kind`
  只支持 `openai` 或 `anthropic`。
- `base_url`
  对应 API 的根地址。
- `api_key`
  访问 Token。必须替换掉 `PUT_YOUR_TOKEN_HERE`。
- `model`
  模型名。
- `max_tokens`
  单次响应的 token 上限。
- `thinking_enabled`
  是否启用推理/思考模式。
- `temperature`
  采样温度。
- `tool_calling_required`
  必须保持为 `true`，否则当前实现会把它判定为非法配置。
- `timeout_seconds`
  当前 provider 的专属超时。若未配置，会回退到 `[router].default_timeout_seconds`。

### 3.10 聊天 provider 和 embedding provider 的区别

这个仓库里的 provider 不是“声明了就一定会出现在 NPC 菜单里”。

对于聊天 provider，至少要满足这些条件：

- `kind` 是 `openai` 或 `anthropic`
- `base_url` 有值
- `api_key` 不是占位符
- `model` 有值
- `tool_calling_required = true`
- 模型名看起来不能像 embedding 模型

因此：

- `deepseek-chat` 这类聊天模型通常会出现在 NPC 的 Provider 列表里。
- `BAAI/bge-large-zh-v1.5` 这类 embedding 模型通常不会出现在 NPC 的 Provider 列表里。

### 3.11 推荐配置范式

最稳妥的做法是至少准备两个 provider：

1. 一个聊天模型 provider
2. 一个 embedding provider

示例：

```toml
[router]
default_timeout_seconds = 45
max_retry_count = 1
tool_loop_max_rounds = 4
retry_backoff_milliseconds = 1500
enable_verbose_debug = true

[embeddings]
provider_name = "embedding"

[perception]
npc_radius_tiles = 100

[broadcast]
max_hops = 5

[providers.deepseek]
kind = "openai"
base_url = "https://api.deepseek.com/v1"
api_key = "sk-替换成你的聊天模型密钥"
model = "deepseek-chat"
max_tokens = 1536
thinking_enabled = false
temperature = 0.7
tool_calling_required = true
timeout_seconds = 20

[providers.embedding]
kind = "openai"
base_url = "https://api.siliconflow.cn/v1"
api_key = "sk-替换成你的向量模型密钥"
model = "BAAI/bge-large-zh-v1.5"
max_tokens = 1536
thinking_enabled = false
temperature = 0.7
tool_calling_required = true
timeout_seconds = 20
```

### 3.12 常见配置错误

#### 错误 1：控制台提示没有可用于聊天的 provider

常见原因：

- `api_key` 还是占位符
- `model` 为空
- `tool_calling_required = false`
- 你配置的是 embedding 模型，却拿它当聊天模型用

#### 错误 2：`embeddings.provider_name` 指向不存在的 provider

把：

```toml
[embeddings]
provider_name = "embedding"
```

里的名字改成你真实声明过的 provider 名。

#### 错误 3：Anthropic provider 被用作 embedding

当前实现不支持。  
解决方式是单独再配一个 openai-compatible embedding provider。

#### 错误 4：Provider 没出现在游戏内列表

先看 SMAPI 控制台里是否有 `mod.toml 配置问题`。  
只要 provider 没被判定成“可用于聊天”，它就不会出现在 NPC LLM 菜单里。

## 4. 编译教程

### 4.1 编译前准备

这个项目的 `TargetFramework` 是 `net6.0`，并且引用了：

- `Lib.Harmony`
- `Pathoschild.Stardew.ModBuildConfig`

因此编译前建议准备：

- .NET 6 SDK
- Stardew Valley 本体
- SMAPI
- 可访问 NuGet 的网络环境

### 4.2 为什么这个项目不能只看普通 `dotnet build`

这个仓库用了 `Pathoschild.Stardew.ModBuildConfig`。它会额外帮你做几件事：

- 尝试自动探测游戏目录
- 提供 `GamePath` / `GameModsPath`
- 构建后自动部署到 `Mods`
- 在 `bin` 目录生成可发布 zip

所以它不是单纯只出一个 DLL 的普通类库工程。

### 4.3 最稳妥的命令行编译方式

如果你的游戏路径是 Windows 原生路径，可以这样构建：

```bash
dotnet restore StardewMod.sln
dotnet build StardewMod.sln -c Debug -p:GamePath="D:\\SteamLibrary\\steamapps\\common\\Stardew Valley"
```

发布构建：

```bash
dotnet build StardewMod.sln -c Release -p:GamePath="D:\\SteamLibrary\\steamapps\\common\\Stardew Valley"
```

如果你是在 WSL 或类 Unix 环境里运行 `dotnet`，则可以传入对应的挂载路径，例如：

```bash
dotnet build StardewMod.sln -c Debug -p:GamePath="/mnt/d/SteamLibrary/steamapps/common/Stardew Valley"
```

Linux 原生环境更推荐直接使用仓库脚本：

```bash
./scripts/build-linux.sh
```

脚本会依次尝试：

- `STARDEW_GAME_PATH`
- `GAME_PATH`
- Linux Steam 默认目录
- Flatpak Steam 默认目录
- 常见 GOG 目录

非默认安装位置可以显式指定：

```bash
./scripts/build-linux.sh \
  --game-path "/mnt/games/SteamLibrary/steamapps/common/Stardew Valley" \
  --configuration Release
```

参数含义：

- `--game-path`：包含 `Stardew Valley.dll` 和 `StardewModdingAPI.dll` 的游戏目录。
- `--configuration`：`Debug` 或 `Release`，默认 `Release`。
- `--output`：校验后发布 zip 的输出目录，默认 `artifacts/linux/`。

构建完成后，脚本会运行 `scripts/verify-mod-package.py`。它会验证 zip CRC、危险路径、反斜杠路径、大小写冲突、`manifest.json`、入口 DLL、`mod.toml` 和聊天气泡贴图，防止 Windows 上看不出问题的包到 Linux 后才因文件名大小写失败。

### 4.4 构建产物在哪里

当前仓库已有历史构建产物，输出格式大致如下：

```text
bin/Debug/net6.0/StardewMod 1.0.0.zip
bin/Release/net6.0/StardewMod 1.0.0.zip
```

同时还会生成：

```text
bin/Debug/net6.0/StardewMod.dll
bin/Release/net6.0/StardewMod.dll
```

但实际安装时，更推荐使用生成好的 zip，而不是直接手工拷贝 `bin/Debug/net6.0` 整个目录。原因是发布 zip 会把模组目录结构整理成可直接解压到 `Mods` 里的形式。

### 4.5 调试构建和发布构建的区别

- `Debug`
  适合本地开发、排查问题、频繁改代码。
- `Release`
  适合打包发布，zip 会放到 `bin/Release/net6.0/`。

### 4.6 如果自动探测不到游戏路径

优先做法：

- 直接在命令行传 `-p:GamePath="你的游戏目录"`。

如果你想长期固定路径，可以按 SMAPI 官方 `ModBuildConfig` 文档配置全局 `stardewvalley.targets` 或项目属性。

### 4.7 如果你只想打包，不想自动部署到 Mods

可以额外关闭自动部署：

```bash
dotnet build StardewMod.sln -c Release -p:GamePath="D:\\SteamLibrary\\steamapps\\common\\Stardew Valley" -p:EnableModDeploy=false
```

这样更适合纯打包或 CI 场景。

### 4.8 GitHub Actions 的 Linux 构建

仓库中的 `.github/workflows/linux-build.yml` 会在以下场景执行：

- push 到 `master`
- Pull Request
- 手动 `workflow_dispatch`

它会调用同一个 `scripts/build-linux.sh`，并把 `artifacts/linux/*.zip` 上传为 Actions artifact。

SMAPI 官方构建包虽然跨平台，但编译时仍需要游戏与 SMAPI 程序集。因此这个 workflow 使用 `self-hosted + linux` runner，而不是假设 GitHub 托管 runner 自带游戏。配置步骤：

1. 在 Linux runner 上合法安装 Stardew Valley 和 SMAPI。
2. 给 runner 保留 `self-hosted`、`linux` 标签。
3. 在仓库 Actions Variables 中设置 `STARDEW_GAME_PATH`。
4. 确保 runner 账号能读取该目录。

手动运行 workflow 时，可以通过 `game_path` 输入覆盖仓库变量。

## 5. 一个推荐的开发-测试流程

1. 先改代码或改 `mod.toml`。
2. 执行 `dotnet build`。
3. 用 SMAPI 启动游戏。
4. 进存档后按 `L` 打开菜单。
5. 在 `NPC LLM` 中选择一个 NPC，先确认 provider 能正常显示。
6. 用 `npc_llm_prompt` / `npc_llm_state` 验证链路。
7. 检查 `NpcMemories/<存档>/<NPC>/` 下是否生成预期文件。
